## Usage guidelines

### When to use

Use a Progress Bar to show progress through a process with a known number of steps, such as the questions in a form.

### When not to use

Do not use a Progress Bar for loading, such as while a file is uploading. Show the actual loading progress with a different component instead or use a Spinner if the duration is unknown.

Do not use a Progress Bar for an unknown or indeterminate amount of progress. Use a Spinner instead.

Do not use a Progress Bar to show the status of a multi-step process, such as the handling of a permit application. Use a Progress List instead: it can show which steps are completed, current or upcoming, not just how far along the process is.

### How to use

Always provide `max`, `text` and `value`. All three are required.

`text` is not calculated from `value` and `max`. Provide it yourself, for example ‘4 van de 10 stappen’. This is necessary because a text like ‘nog maximaal 8 vragen’ cannot be derived from those two numbers, and it means the text can never be forgotten.

Only show a total if it holds true for the entire process. If you are not sure the total will stay accurate, use a text such as ‘nog maximaal 8 vragen’ instead of a fixed total.

A Progress Bar does not announce changes to its value itself. If a change should be announced to screen reader users, let the page announce it with a single status message. Describe in your own documentation when and how that message changes.

Use on a white background only.

## Features

A Progress Bar shows a known amount of progress as a filled portion of a bar, together with a `text` that is always shown alongside it.

The bar animates when its value changes, drawing attention to the increase in progress. It does not animate when the page is first shown, so a form with one question per page does not look like it restarts from zero on every page.

## Design

The `text` is shown centred above the bar.

Below the text is the track. It has a rounded border and a background. The border radius is the same as the height of the track, which gives it fully rounded ends.

Inside the track is the `fill`. The fill shows how much of the progress is completed. Its width is controlled with CSS using `transform: scaleX()`, based on `value / max`.

We use our own fill instead of the browser's default `<progress>` styling. This gives us full control over how the Progress Bar looks and keeps it consistent across browsers.

The Progress Bar and its track are always 100% wide. They do not add extra space around themselves.

For now, the Progress Bar can only be used on a white background.

### Animation

The fill uses CSS `transform` instead of the browser's default `<progress>` styling. This allows the animation to be handled entirely with CSS.

The fill only animates when value changes. It does not animate when the Progress Bar first appears.

The animation is only enabled when the user has not enabled reduced motion. Users who prefer reduced motion see the fill move directly to its new value without an animation.

## Accessibility

The Progress Bar uses the native `<progress>` element so screen readers can understand the current progress. The `value` and `max` props are passed to the element.

The `<progress>` element is visually hidden. The visible `text` and fill use `aria-hidden`, while `aria-label={text}` makes sure the text is read once by screen readers.

The Progress Bar does not announce value changes itself. If a change needs to be announced, the containing page should provide a separate status message.

In forced colors mode, the border and fill use system colours to remain visible.

In right to left (`dir="rtl"`) layouts, the fill grows from right to left.

The track and fill keep their colours when printed.
