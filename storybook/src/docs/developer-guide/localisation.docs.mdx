# Localisation

Localisation covers two related tasks.
Declare the language of your content so browsers and assistive technologies interpret it correctly, and tell components which language and region to format their output in.

## Language

Declare the human language of your content with the HTML `lang` attribute.
This helps browsers, screen readers, and search engines interpret it correctly.

### Specify the language for the entire document

It is mandatory to explicitly indicate in which language the content of your page is.
With the correct language set, your website will work better.
Screen readers will know what language to use for speech.
It is also helpful for search engine optimization (SEO).

Specify the language on your website’s `<html>` element.
After all, the contents of elements in the `<head>`, such as `title` and `meta`, also contain content in the same language.
That is outside the scope of the components of the design system.
That is why you have to remember to do this properly yourself.

```html
<html lang="nl">
  …
</html>
```

### Highlight elements in another language

If a specific element is in another language, indicate this there.

For example, for a link to an English site or page in a menu:

```html
<nav>
  <ul>
    <li><a href="https://mijn.amsterdam.nl/">My Amsterdam</a></li>
    <li><a href="https://www.amsterdam.nl/en/" lang="en">English site</a></li>
  </ul>
</nav>
```

### Do not specify the region

The language tag `nl` is sufficient.
Expanding it with the region subtag `nl-NL` is not necessary:

> The golden rule when creating language tags is to keep the tag as short as possible.
> Avoid region, script or other subtags except where they add useful distinguishing information.
> – [W3C Internationalization Activity](https://www.w3.org/International/articles/language-tags/)

## Locale

Some components render their own text, such as weekday and month names.
Set the language and region they format it in with the `locale` prop.

### Localise components

The [Calendar](/docs/components-navigation-calendar--docs) and [Date Picker](/docs/components-forms-date-picker--docs) render weekday names, month names, and accessible date labels in the language of their `locale` prop.
When you omit it, both default to `nl-NL`.

The prop accepts a [BCP 47 language tag](https://www.w3.org/International/articles/language-tags/).
Unlike the HTML `lang` attribute, including a region subtag is appropriate here.
The JavaScript `Intl` API can produce different output for different regional variants of the same language.

These locales have been tested:

- `nl-NL` – Nederlands (Dutch), the default
- `en-GB` – English
- `de-DE` – Deutsch (German)
- `fr-FR` – Français (French)
- `tr-TR` – Türkçe (Turkish)
- `ar-MA` – العربية (Arabic)

`locale` only drives the text that `Intl` generates.
Both components also have accessible names and navigation button labels that stay in their default language until you translate them, so set those in the same language to avoid a mix.
For right-to-left languages like Arabic, also add `dir="rtl"` to the component or to a containing element.

If your app uses one of these components in multiple places with the same language, a small wrapper component avoids repeating these props:

```tsx
import type { CalendarProps } from "@amsterdam/design-system-react";

import { Calendar } from "@amsterdam/design-system-react";

const ArabicCalendar = (props: CalendarProps) => (
  <Calendar
    accessibleName="التقويم"
    dir="rtl"
    locale="ar-MA"
    nextMonthButtonLabel="الشهر التالي"
    nextYearButtonLabel="السنة التالية"
    previousMonthButtonLabel="الشهر السابق"
    previousYearButtonLabel="السنة السابقة"
    {...props}
  />
);
```

The same pattern applies to the Date Picker, which also takes `rangeStartAccessibleName` and `rangeEndAccessibleName` in range mode.

### Native form controls

Native form controls render some of their text themselves.
For example, `<input type="time">` orders and formats its hour and minute fields according to the browser’s own locale, not the page’s `lang` or `dir`.
This is browser behaviour that pages cannot override.

### Mirror directional icons

Icons that imply a reading direction or depict movement that follows the reader’s natural flow flip in a right-to-left context.

The design system’s own directional icons handle this automatically: each carries a `data-directional="true"` attribute on its root `<svg>`, and the [Icon](/docs/components-media-icon--docs) styles mirror any icon with that attribute under `dir="rtl"`.

The [Calendar](/docs/components-navigation-calendar--docs) and [Date Picker](/docs/components-forms-date-picker--docs) navigation chevrons are one example.
When you supply your own directional icon anywhere, give it the same attribute so it mirrors as well.

## Relevant WCAG requirements

- [WCAG 3.1.2](https://www.w3.org/TR/WCAG22/#language-of-parts): indicate the language of any passage or phrase that differs from the page’s default language
